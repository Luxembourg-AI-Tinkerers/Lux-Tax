triggered, so it is stated explicitly rather than buried.

## 3. Worth considering

### F1 — the package re-derives the taxpayer/spouse split instead of the calculation's filer selection

- **Position.** `apps/api/src/modules/filing/filing.service.ts:255-256`
  (`primaryMember = members.find(role === 'PRIMARY_FILER') ?? members[0]`),
  `:262-281` (`ownerOf`: any owner that is not the primary is "spouse"),
  `:205-213` (member query — no `status` filter), against
  `apps/api/src/modules/calculations/class-resolution.ts:173-208`
  (`selectFilerMembers`) and `calculations.service.ts:116-140` (the calculation
  calls it with the acting user, filters `status: 'ACTIVE'`, and drops a
  former spouse for WIDOWED/DIVORCED).
- **Problem.** The two layers use different definitions of "primary". The
  calculation promotes the acting CO_FILER to primary (`selectFilerMembers`
  returns `{primary: u2, spouse: u1}` for actor `u2`); the filing service always
  makes the `PRIMARY_FILER` member primary and never reads the acting user, the
  membership status, or `spouseEndsAtEvent`.
- **Impact (probe).** Household `u1 PRIMARY_FILER Alice`, `u2 CO_FILER Bob`,
  salaries 40 000 / 30 000, package generated by `u2`: 701 = Alice 40 000,
  702 = Bob 30 000 — the reverse of the calculation's split for that actor.
  With a third `VIEWER` member holding a salary fact, both the spouse and the
  viewer land on case **702 as two separate rows** (probe S3: 702 Deceased
  25 000 + 702 Read-only 10 000). A `PENDING_INVITATION`/`REMOVED` membership is
  not filtered here even though `approveReturn` (`filing.service.ts:75`) filters
  `ACTIVE`. No amount is lost or duplicated; only the column/person attribution
  can disagree with the stored calculation.
- **Fix direction.** Reuse `selectFilerMembers(members.filter(status ===
  'ACTIVE'), userId)` for `primaryUserId`/`spouseUserId` and mark a fact as
  spouse only when `fact.ownerId === spouseUserId` (not "anyone else").

### F2 — the unsupported-code warning misclassifies `C`, and `103`'s label still says "(C)"

- **Position.** `packages/tax-engine/src/engine.ts:246-251` (and the twin at
  `filing.service.ts:344-350`); `packages/tax-engine/src/forms/certificate160.ts:78`
  (`103` `labelFr: 'Cotisations sociales déductibles (C)'`), `:112-120` (`C`
  note: "a section-A gross-pay component … not the section-B 103 deduction").
- **Problem.** The `C` row explicitly documents that it is a **note-3** letter
  (section-A gross-pay component), yet the warning it produces says `C` "is a
  certificate **withholding-base label**" — the note-6 category. At the same
  time the `103` label still carries the "(C)" tag the corrected note denies, so
  the 160 control step prints "Cotisations sociales déductibles (C) (modele
  160)" for 103 while warning that C is a different thing.
- **Impact.** A user reconciling a certificate that carries both a `C` line and
  a `103` line gets two contradictory statements from the same package. No
  amount is affected (both paths leave the return unchanged / map 103 to social
  contributions).
- **Fix direction.** Use a neutral phrase in the unsupported warning ("a
  certificate label the engine does not map"), and drop "(C)" from the `103`
  label. The `C`/`R` tests assert on the phrase "withholding-base"
  (`tax-engine.spec.ts:1563-1581`), so update them with the wording.

### F3 — an unlisted multi-letter certificate code is still dropped in silence

- **Position.** `packages/tax-engine/src/forms/certificate160.ts:244-256`.
- **Problem.** `isCertificate160FieldKey` accepts the `code_` prefix, a bare
  three-digit key, a **single** letter, or a table key. A bare two-to-four-letter
  code outside the table — `'ZZ'`, `'FDD'`, `' ABC '` — returns `false`,
  falls through the category switch in `engine.ts:262-330` and the `default:
  break` in `filing.service.ts:584`, and produces neither a value nor an
  `unsupportedCertificateCodes` entry. (`code_FDD` does warn, because of the
  prefix.)
- **Impact.** Same failure class M1 closed, for a code the table does not list.
  Not live today: every code printed by the 160F (note 3: S/C/R/P; note 6:
  FD/FO/FFO/DS/FDS/CE/AC/LRCP) is in the table, so no current fixture triggers
  it. It becomes live the first time a real certificate carries a new code.
- **Fix direction.** Treat any all-uppercase key of 1–4 letters (no lowercase) as
  certificate-shaped; engine field keys are camelCase, so the collision risk is
  nil.

### F4 — `INSTRUCTION` rows are rendered as if they were boxes to copy

- **Position.** `apps/web/src/components/FilingPackageView.tsx:248-275` (no
  reference to `kind`); producers at `filing.service.ts:468-483` (foreign) and
  `:603-615` (Art. 114 loss).
- **Problem.** The package table has no `kind` column or badge, so the foreign
  pointer renders as "RD · case 1081/1082" with the **foreign income** as its
  value and a working Copy button — the same shape as a real case. The Art. 114
  row renders as "Recap · case computed" with the loss amount.
- **Impact.** A user following the table can copy the foreign income (8 000 in
  the probe) into RD 1081/1082, which is the foreign-tax **credit** line, not an
  income line; the label says what to do, but the row's affordance says
  "copy this number here".
- **Fix direction.** Render a badge from `kind` and suppress (or replace with
  "see note") the copy action for `INSTRUCTION` rows; keep the amount only as
  traceability, not as a value to paste.

### F5 — two e2e specs still assert the pre-LEG-7 package shape
