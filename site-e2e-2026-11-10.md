# Full site e2e — 10 November 2026

**Scope:** the web application (`apps/web`) driven in a real browser against the real API and
PostgreSQL. This is the first time the app was built or rendered: `apps/web/node_modules` had never
existed, so `next build` had never run and no page had ever been served.

Everything below was executed on this machine, in Chromium, against `localhost:3000` → `localhost:3001`.

## The seven

| # | Defect | Blast radius |
|---|---|---|
| **S1** | The CORS preflight answered **`GET,HEAD,POST`** only. | Every `PUT`/`PATCH`/`DELETE` from the browser failed as *"Failed to fetch"*. Saving the questionnaire, editing or deleting a fact, changing document visibility, saving a freelance profile, saving notification preferences — the **entire editing surface** was dead. |
| **S2** | The API client declared `Content-Type: application/json` on **bodyless** POSTs. | Fastify rejected `POST /calculate`, `/approve`, `/read-all`, `/rollover`. The **first tax calculation from the UI was impossible**. |
| **S3** | The extractor matched the substring **`'certif'`** (inside "certificat") in its training-course branch. | The app's own sample salary certificate came back as a **CHILDCARE INVOICE** with `trainingCourseExpense €76,800`. Confirming it would have booked a €76,800 deduction from a salary certificate — a severe understatement of tax. |
| **S4** | The withholding pattern required "retenue d'imp**ô**t"; the sample says "impot". | Codes **105 and 141 were silently dropped** from the same certificate: half the data lost, with no warning. |
| **S5** | Accepting an invitation never compared the invited address, and the upsert rewrote the member's role. | A **PRIMARY_FILER was demoted to CO_FILER** by opening a CO_FILER invitation (observed in the database), and any signed-in user holding a link could join a household. |
| **S6** | The assessment panel never filled the objection deadline or follow-up date after import. | Two fields stayed blank until a page reload, although the API returned both. |
| **S7** | "Both spouses can now review" on a **single-filer** return. | Wrong copy on the most common household shape. |

### What the fixes look like

- **S1** — explicit `methods` and `allowedHeaders` in `enableCors`, with the reasoning recorded next
  to it: a preflight is something server-to-server tests never send.
- **S2** — one line in `packages/api-client`: the header is attached only when there is a body.
- **S3/S4** — keyword matching runs on a **de-accented** copy of the text, the `'certif'` trigger is
  gone, and the four certificate lines are read **by code** (`101`, `103`, `105`, `141`), accepting
  both `101. …` and `Code 101 - …`. That makes the parse independent of accents, wording and language.
- **S5** — the accepting account must match the invited e-mail (403 otherwise); an existing
  membership keeps its role; a revoked invitation is refused.
- **S6/S7** — state filled from the import response; the spouse clause only appears when the
  household really has more than one active member.

### DS 1553 — resolved: the two figures measure different scopes

The first pass recorded "DS 1553 shows EUR 3,200 while the engine deducted EUR 3,700 — one of the
two is wrong". **Neither is.** Checked against the persisted snapshot of the e2e workspace and
against a fresh engine run:

| Line | Amount | Meaning |
|---|---|---|
| DS **1503** (Art. 111bis) | 3,200.00 | declared pension-savings premium, after the cap |
| DS **1553** | 3,200.00 | total of the expenses covered by the statutory minimum (cases 1301–1552) |
| DS **1609** (LRCP) | 0.00 | none declared |
| DS **1611** (Art. 112 donations) | 500.00 | deducted *in addition* to the forfait |
| engine `specialExpensesTotal` | **3,700.00** | `max(forfait 480, covered 3,200) + LRCP 0 + donations 500` |

3,200 + 0 + 500 = **3,700** — the package reconciles to the engine exactly. Art. 112 donations are
not part of the "covered by the forfait" total (they are additional by law), so folding them into
1553 would have *double-counted* them. The statutory minimum (480 here) replaces the covered total
only when it is **higher**, and that branch emits an explicit INSTRUCTION on 1553 instead of
silently overwriting the figure.

Pinned by `apps/api/test/form100-case-map.spec.ts` — four tests assert the split, the
`1553 + 1609 + 1611 = total` identity, the case mapping, and the "forfait above covered ⇒
instruction" branch, so a later change cannot fold the donation back into 1553.

## How it was run

`pnpm install` does not finish on this machine (about ten packages per minute, filesystem bound), so
the app was served through a flat junction farm over the already-populated pnpm store. This affects
**how** it ran, not what it proves. The `apps/web/node_modules` and `apps/api/node_modules` junctions
are git-ignored.

The web server and API are still running (`:3000`, `:3001`) against the throwaway database
`luxtax_site` if you want to click through it yourself.
